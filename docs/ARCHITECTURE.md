# Architecture

Helix Trader is a Rust workspace built on NautilusTrader: the main crate, `helix-trader` at the root, and two adapters, `ctrader` in `crates/ctrader`, a Nautilus adapter for Spotware's cTrader Open API, and `lse` in `crates/lse`, a Nautilus data client for London Strategic Edge's market data. Nautilus owns data, simulation, execution and the portfolio; this repository adds what Nautilus lacks.

## Design rules

- Check Nautilus for a feature before implementing it here. Strategies use the plain Nautilus API, without a wrapper layer.
- Venue code lives in `src/venues`, one module per venue holding its history and live clients. Shared routing gives each venue a row naming, each on its own, the source of its instrument definitions (a source, or the catalog alone, written by hand), its history and its live data, and its broker, if one trades it; each caller asks the row for the part it needs, and catalog, live, backtest, orders and fill-catalog code do not branch on venues. Custom data of no instrument, such as an LSE reference series, has no venue and no row: data requirements carry it as its Nautilus data type, keyed by its identifier, and its type names its source. A fill's requests name the client that answers each, which Nautilus' data engine routes by before any venue route, so the fill's clients take no venue routes and one venue can mix sources: GLBX, XNAS and OPRA take their definitions from Databento, their history and live data from LSE and their orders from IB. On the live node every venue a run reads is routed to its live data's client and no data client is the default route, since Nautilus' data engine makes the first data client on no venue it registers the default (`DataEngine::register_client`, `crates/data/src/engine/registry.rs:44`) and refuses another made the default after it (`set_default_client`, `registry.rs:101`), and the node builder registers its clients in its `HashMap`'s order (`crates/live/src/node/builder.rs:94`, `:642`), so with LSE's and IB's data clients, both on no venue, making IB's the default failed the build whenever LSE's came first; orders of no broker's own route go to IB's execution client, the execution engine's default, which it makes no client implicitly. Broker capabilities are recorded here because Nautilus exposes position mode only on a built execution client and does not expose its order-flag restrictions. Normal backtests use the broker's position mode; dataset runs use hedging for every venue. A venue no broker trades is only read: a backtest simulates it with no money and Nautilus' default position mode. Venue flags are composed per command. Nautilus factories, configs and `RoutingConfig` are the seam; venue needs differ too much for a homogenizing trait to hide. The broker-independent cTrader crate needs no helix code: add a broker with a routing-table entry and a small venue module, without a new variant or branch. See [`venues/mod.rs`](../src/venues/mod.rs) for routing, capabilities and adding brokers.
- One process runs one strategy, which decides its own trades. The strategy configuration defines instruments and cadence for catalog filling, backtesting and live operation.
- The same strategy type and Nautilus engine run in backtest, paper and live. See [strategy authoring](../src/strategy/README.md) and [backtesting](../src/backtest/README.md) for the differences in operation.
- Model strategies read published files rather than training as they trade. Backtest and live share the model store; a backtest builds and trains in its own process with sequential, disposed nodes, while live retrains in a child process. A never-retrained strategy trains each model once and has no live retrain actor. The schedule governs training, backtests, scores and live alike; see [model scheduling](../src/model/README.md#scheduling) and [live retraining](../src/live/README.md#retraining).

## Process constraints

Run no two Nautilus nodes of a process at once: a node's message bus is thread-local, while logging and the Tokio runtime are process-wide. A process may run backtest nodes one after another, each disposed before the next starts, as Nautilus documents: a backtest of a model strategy builds its dataset, trains and then runs so, in one process. A live node is the one node of its process while it runs, so its retrains are child processes. Backtest integration tests run their nodes at once, one per test thread, which Nautilus does not support: each thread has its own message bus and registries, but the logger, with the logging mode and clock each backtest switches, the logging worker and the Tokio runtime are the process's, shared by every node, so log timestamps may reflect another test's simulated time. Live nodes also install a tracing subscriber and take SIGINT; run live test modules in separate processes.

Nautilus owns the global logger, and code logs through `log` macros. A backtest node installs Nautilus' logger from the config it is given; the live run and fill-catalog install it themselves (`init_logging`) before any node, since the live clients are set up before the node is built and a fill may run no node, and a node built afterwards keeps it. No other logger is installed. Backtests use `BacktestNode`, a fresh node per run, not parameter sweeps.

## Dependencies and tests

The root `Cargo.toml` is the source of truth for the Nautilus pin, one for the workspace (`[workspace.dependencies]`). Its git version supplies OKX fixes and historical request and catalog write-back support needed by warmup. Treat upgrades as deliberate changes: read release notes and run the full test suite. If an upgrade changes golden dataset rows, bump the dataset version; see [model guidance](../src/model/README.md).

Unit tests sit with the module they test; integration tests are under `tests/backtest/` and `tests/live/`. `cargo test` and `cargo clippy` at the root cover every crate; `cargo test -p ctrader` and `cargo test -p lse` run an adapter's tests alone. See the [root test guidance](../README.md) for venue gates and process isolation.
