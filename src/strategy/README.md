# Writing a strategy

A strategy implements Nautilus' `Strategy` trait; backtest and live do not depend on a concrete strategy. One process runs one strategy. Use [`ema/`](ema/) and the maintained [`config/ema.toml`](../../config/ema.toml) as the non-model example.

## Authoring

1. Create `strategy/<name>/` with a `Part` for strategy-specific config and rules, a constructor, thin Nautilus wiring, and pure decision modules. Make `Part::reads` answer exactly the series the strategy subscribes to and uses for indicators.
2. Register state as at least one Nautilus indicator in `DataActor::on_start`. Decide only when `self.core().indicators_initialized()?` is true; Nautilus feeds registered indicators before the strategy's handler. A model strategy's handle gates its decisions on its own features and target instead, its features being registered for their bars alone. Keep decisions free of I/O and look-ahead, use the strategy clock rather than the system clock, and seed randomness from config.
3. Build a `Warmup` from the data requirements, feed the indicators through it, and forward historical responses and time events as needed; a model strategy's data hooks are `model_data_hooks!`, written once for every one. Use `strategy::orders::Trade` for trades, sent at a stake (unless the strategy does not size by risk, see [Configuration and series](#configuration-and-series)), refuse an inverse traded instrument (`orders::refuse_inverse`) and rearm open trades on start.
4. Export `pub fn visit<V: Visitor>(visitor: V) -> V::Output` from the folder's `mod.rs`, calling `visitor.plain::<S>()` for a strategy trading on no model (it implements `PlainStrategy`) or `visitor.model::<S>()` for a model strategy. Nothing else registers it: `build.rs` declares each folder of `strategy/` holding a `mod.rs` as a module and a command-line name, both the folder's name, a lowercase identifier. Non-model strategies refuse train and dataset commands. Test the pure decisions and config rules, then exercise wiring on a fixture backtest.

**Keeping a strategy private:** list its folder in `.git/info/exclude` (`/src/strategy/<name>/`), never in `.gitignore`, so that no committed file names it. A checkout without the folder builds without the strategy.

**Formatting:** the strategies reach the crate through the build script's generated `include!`, which `cargo fmt` does not follow. Format them with `rustfmt src/strategy/*/mod.rs` after `cargo fmt`.

**Model strategies:** for features, decisions, labels, training, stores, meta-labeling or version bumps, read the [model guide](../model/README.md). `model_ema/` and [`config/model_ema.toml`](../../config/model_ema.toml) are the example. For run orchestration see [backtest](../backtest/README.md); for live operations see [live](../live/README.md).

Nautilus' `nautilus_strategy!` starts a strategy with `Strategy::on_start`, which reactivates GTD timers when `manage_gtd_expiry` is set, then `DataActor::on_start`, where the strategy's own start goes; it need not call the former.

## Configuration and series

`StandardConfig::load` parses and validates the strategy's TOML before a node starts. `StandardConfig` owns the common `[base]`, `[data]`, `[indicators]`, `[trade]` and, for model strategies, `[model]` tables; `Part` owns top-level strategy fields, instrument count, whether it trades on a model or sizes its trades by risk, default base, declared indicators and additional rules. Unknown keys are rejected, except that Nautilus' `bar_spec` deserializer ignores extra keys. Parsing reports its first error; subsequent validation collects violations.

`[data].series` is exactly what `Part::reads` says the strategy reads: missing, extra and duplicate series are errors. The EMA reads only the first bars series of its traded instrument. `[trade].instruments` lists each instrument traded by its `instrument_id` alone: no instrument has a size of its own, and a `trade_size` is refused as the config is read, at its value, pointing to `[trade].risk`. `[trade].risk` is the fraction of equity a trade risks at the config's stake, written as a percentage (`"0.5%"`) above 0% and below 100%; a bare number is refused, as it could be a fraction or a percentage. A strategy that does not size its trades by risk, one holding a target exposure such as a rebalancer keeping target weights, declares `Part::SIZES_BY_RISK` false: its `[trade]` takes no `risk`, which is refused as an unknown key, and `config.stake()` panics, as `config.model()` does for a strategy without a model. It sizes its orders itself through the plain Nautilus API (`portfolio().equity`, its positions from `cache()`, `order().market`, `submit_order`), not through `orders::Trade`. Every other strategy keeps the default and requires `risk`; a model strategy must, its model being priced at the reference stake. When no series prices a traded instrument (its bars, quotes or trades), its quotes are added to data requirements for execution, not to `[data].series`: Nautilus prices a market order from quotes, trades or external bars, so depth, book deltas or custom data alone would have its orders denied. Consumers use `data_requirements()` rather than reconstructing requirements from config.

Declare each indicator name and argument type in `Part::INDICATORS`, build it from `config.indicators`, and register it for its input. Indicator tables not declared by the strategy are rejected. The shared config validates the declared arguments and strategy rules. A model strategy's features are declared the same way; its code hands each feature's table to the feature set rather than building it, and the TOML marks no role (see the [model guide](../model/README.md)). An argument type is `Deserialize` and `Serialize`, since a feature's arguments enter the fingerprint.

Bars are time-aggregated internal bars; `from` makes them composite from external source bars. Internal source bars are rejected because live warmup cannot request them. Tick series may be quotes, trades, book depth, book deltas or instrument-keyed custom data, which no fill-catalog source supplies. Custom data of no instrument, such as an LSE reference series, is not a tick series: `[data].custom` lists it, each entry a Nautilus data type by its type and metadata, `{ data = "Custom:LseRow", metadata = { source = "bond_yields", symbol = "US10Y" } }` for LSE's daily 10-year US yield, keyed as its source keys it (`venues::custom_data_type`); a type no source serves, metadata other than a source and a symbol, or an entry listed twice is refused. No `Part::reads` answers it, so a strategy lists it beside its series and subscribes to its data type itself. Data requirements carry it apart (`DataRequirements::custom`): fill-catalog fills it from LSE and a backtest replays it over its window, each row when its values are known (a date's at its end), registering LSE's type itself; a live run reading any is refused before anything connects, as no source streams it yet. Other custom types must be registered before catalog replay. The strategy subscribes to its own tick and book streams. Consult the [catalog guide](../catalog/README.md) for source availability and [backtest guide](../backtest/README.md) for replay.

A futures root's bars must be internal LAST bars built from its trades; orders must name a contract, not a root. Root tick subscriptions and continuous bars require roll handling; see [rolls](../rolls/README.md) for calendars and transitions.

## Bars and sessions

Internal BID, ASK and MID bars are built from quotes, LAST bars from trades. A bar stamped at close contains ticks in `(open, close]`; quote-bar volume sums quoted sizes, not trades. LAST bars carry no spread. Composite bars aggregate source bars, so their high and low reflect those source intervals. Backtest and live disable empty time bars: a period without a tick or source bar produces no bar rather than a stale flat bar.

A configured session accepts a bar only when its whole span lies within the local day's open and close in the configured IANA time zone. Outside bars neither update indicators nor trigger orders, including during warmup. Omit the session for 24/7 trading; `00:00`–`23:59` excludes the bar closing at midnight. Sessions are rejected with composite bars: composite bars are built and stamped five seconds after close to allow source bars to arrive live, in a backtest and a dataset run as live. Quote-built bars have no such delay, unless the strategy also reads composite bars: the delay is the data engine's, for every time bar it builds.

## Orders and positions

A trade is built without a quantity: `Trade::new` takes its instrument, side, exits, the reference price its exits are set from, and one R, the distance in price from that reference to its stop, or an ATR for a trade ended by its time alone. Its fields are the order module's, so no other code changes its exits or its one R once it is built. A strategy owns how much it risks: the stake, the config's risk times a multiple, 1 at `config.stake()`, scaled by `stake.times(k)` for a positive `k`. `trade.send(strategy, stake)` reads the equity in the instrument's P&L currency of the account its orders are checked against from the strategy's portfolio (`Portfolio::equity`, open P&L included on a margin account), and sizes the trade with Nautilus' `calculate_fixed_risk_position_size`: the stake's fraction of that equity over what its stop is worth on one unit, rounded down to the instrument's size increment and capped at its maximum quantity, no commission counted. The stop it is sized at is one R from the reference on the instrument's tick grid, rounded away from the reference, so a size never risks more than its stake. A size rounding down to zero sends nothing and logs a warning; an account with no equity in the P&L currency sends nothing and logs an error, since equity is not converted. Nautilus' risk engine judges what is sent: a quantity below the instrument's minimum, or a margin beyond the free balance, is denied, and the run goes on. Each entry is tagged with its R in money, its quantity's worth over one R (`R:500.00 USD`), and its stake's multiple (`MULTIPLE:2`), read back with `orders::entry_risk`. Inverse instruments are refused at start, since the sizer reads a P&L as a multiple of a distance in price. A model strategy sends its decision's trade the same way, at a stake of its own (`decision.trade().send(self, stake)`); its model is priced at the reference stake, the config's risk of the dataset balance, through `trade.send_at(strategy, stake, equity, ids)`, which sizes at a fixed equity in place of the account's (see [model strategies](../model/README.md#reference-stake-and-the-strategys-stake)).

The account is the one Nautilus' risk engine checks the orders against (Nautilus' execution guide, `concepts/execution`, "Account selection"): the account the cache registers for the execution client routed for the instrument's venue, else for the default client (`Cache::client_id_for_venue`, then `Cache::account_id_for_client`), else the account issued under the instrument's venue. A live node routes each cTrader broker's venue and OKX to their own clients and makes IB the default client; a backtest routes each simulated venue to its own. IB's account is issued under `IB`, not the exchanges its instruments name (`IBIS`, `IDEALPRO`), and is found through IB's client. The equity is the account's balance plus the open P&L of its positions on the instrument's venue: positions the same account holds on its broker's other venues are left out, as are other processes', which the cache does not hold anyway, one process running one strategy. An account with a base currency reports its equity in that currency alone, so a trade on an instrument whose P&L is in another sends nothing.

A trade's exits hold a `Bracket`, its take profit and stop loss, which produces a Nautilus bracket, or none, which produces a market entry. The time limit starts at send, not fill. Forward time events to `orders::on_time_event` and call `orders::arm_open_trades` on start so cached open trades regain their alerts after a restart. The alert cancels open orders and closes any remaining position; a partial exit does not end the remaining trade.

Leave `oms_type` unset so positions follow the venue. On a netting venue overlapping trades share a position and one trade's time exit closes the whole position, including the other trades' share. On a hedging venue each trade has its own position. The EMA is an example and permits overlap. Its bracket legs and time close are reduce-only except on IB, whose execution client denies them. On IB the two legs of a bracket share an IB OCA group instead, named after the entry and tagged on them besides Nautilus' own tags (`venues::bracket_exits_tag`), so IB reduces the other leg at a partial fill and cancels it at a full one even while the node is down; see [IB](../venues/ib/README.md#trading-and-warmup) for the group's type and what overlap still risks there, and [backtest](../backtest/README.md) for execution limitations.

## Warmup

Live requests history at start and hydrates indicators before the live stream. A backtest requests no warmup: it replays only its requested interval, and indicators initialize on that replay. Start earlier if decisions are needed at a particular time. A dataset build replays the features' warmup before its first day and stores no earlier decisions; see the [model guide](../model/README.md).

`strategy::warmup::Warmup` owns the request and subscription protocol. It first asks the definition of each instrument it warms up that the cache lacks, of the client the venue's row names (its broker's, else its live data source's): the catalog answers first, so `LSEDGE` definitions, which LSE does not publish, come from there, and those the broker clients already cached are left as they are. A composite bar requests its external source bars; other bars request the quotes or trades from which they are built. Every series is asked in windows of 23 hours through Nautilus' time-range requests, each answered and written back on its own, and a run of empty windows does not end one. A window of book deltas whose UTC day's start the catalog holds, earlier windows' write-back included, is read from there and opens with a snapshot of the book at its own start, so a feature reading deltas sees one per window beside the day's. When a request completes, it feeds the bars it built to indicators in chronological order, each once, composite bars included. It keeps the subscription continuous across the request boundary and sizes the live cache for the requested bars. Root continuous bars have a separate path; live currently refuses them, as described in [rolls](../rolls/README.md).

A completed request does not itself enable decisions: indicator initialization does. A model strategy's decisions also wait for every warmup request to complete, as features reading ticks can be initialized on the older windows alone. Live ticks start at the subscription, while older windows are still being answered, and Nautilus holds them for its bar aggregators alone: the warmup hands a model strategy's features the quotes and trades of its responses, holds the live ones until the last window is answered, then hands them over in the order they came, dropping those the history holds. Historical callback errors are logged rather than stopping the run, and an unanswered request leaves its group unfinished. The catalog supplies available history and the live client supplies missing intervals where supported; see [live](../live/README.md) for operational details. Recursive indicators retain a decaying dependence on their initial state even after initialization; allow several periods of history when reproducibility matters.
