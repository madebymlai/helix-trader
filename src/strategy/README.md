# Writing a strategy

A strategy implements Nautilus' `Strategy` trait; backtest and live do not depend on a concrete strategy. One process runs one strategy. Use [`ema/`](ema/) and the maintained [`config/ema.toml`](../../config/ema.toml) as the non-model example.

## Authoring

1. Create `strategy/<name>/` with a `Part` for strategy-specific config and rules, a constructor, thin Nautilus wiring, and pure decision modules. Make `Part::reads` answer exactly the series the strategy subscribes to and uses for indicators.
2. Register state as at least one Nautilus indicator in `DataActor::on_start`. Decide only when `self.core().indicators_initialized()?` is true; Nautilus feeds registered indicators before the strategy's handler. A model strategy's handle gates its decisions on its own features and target instead, its features being registered for their bars alone. Keep decisions free of I/O and look-ahead, use the strategy clock rather than the system clock, and seed randomness from config.
3. Build a `Warmup` from the data requirements, feed the indicators through it, and forward historical responses and time events as needed. Beside it, `subscriptions::Subscriptions` of the requirements' bar types, ticks and custom data of no instrument owns every live subscription, a model strategy's adding its target's ATR's bars, which no strategy declares: started from `on_start` with the time the warmup's start returns, it subscribes to the bars, to each tick series and to the custom data from where the warmup ends, the quotes of the `[trade] conversions` pairs among the ticks, whose history the warmup requests as it does every series of the requirements (see [Warmup](#warmup)). A strategy whose ticks on a root need roll handling (see [Configuration and series](#configuration-and-series)) holds a `rolls::Roller` of the ticks' instruments (`Roller::live`, `Roller::replayed`), started after it from the same time, which alerts before each roll of a root and returns the transition from `on_time_event`: hand it to the subscriptions' `roll`, which moves the root's series to the post contract (see [rolls](../rolls/README.md)). A model strategy's handle holds all three, and its data hooks are `model_data_hooks!`, written once for every one. Use `strategy::orders::Trade` for trades, sent at a stake (unless the strategy does not size by risk, see [Configuration and series](#configuration-and-series)), refuse an inverse traded instrument (`orders::refuse_inverse`) and rearm open trades on start.
4. Export `pub fn visit<V: Visitor>(visitor: V) -> V::Output` from the folder's `mod.rs`, calling `visitor.plain::<S>()` for a strategy trading on no model (it implements `PlainStrategy`) or `visitor.model::<S>()` for a model strategy. Nothing else registers it: `build.rs` declares each folder of `strategy/` holding a `mod.rs` as a module and a command-line name, both the folder's name, a lowercase identifier. Non-model strategies refuse train and dataset commands. Test the pure decisions and config rules, then exercise wiring on a fixture backtest.

**Keeping a strategy private:** list its folder in `.git/info/exclude` (`/src/strategy/<name>/`), never in `.gitignore`, so that no committed file names it. A checkout without the folder builds without the strategy.

**Formatting:** the strategies reach the crate through the build script's generated `include!`, which `cargo fmt` does not follow. Format them with `rustfmt src/strategy/*/mod.rs` after `cargo fmt`.

**Model strategies:** for features, decisions, labels, training, stores, meta-labeling or version bumps, read the [model guide](../model/README.md). `model_ema/` and [`config/model_ema.toml`](../../config/model_ema.toml) are the example. For run orchestration see [backtest](../backtest/README.md); for live operations see [live](../live/README.md).

Nautilus' `nautilus_strategy!` starts a strategy with `Strategy::on_start`, which reactivates GTD timers when `manage_gtd_expiry` is set, then `DataActor::on_start`, where the strategy's own start goes; it need not call the former.

## Configuration and series

`StandardConfig::load` parses and validates the strategy's TOML before a node starts. `StandardConfig` owns the common `[base]`, `[data]`, `[indicators]`, `[trade]` and, for model strategies, `[model]` tables; `Part` owns top-level strategy fields, instrument count, whether it trades on a model or sizes its trades by risk, default base, declared indicators and additional rules. Unknown keys are rejected, except that Nautilus' `bar_spec` deserializer ignores extra keys. Parsing reports its first error; subsequent validation collects violations. The loaded `[base]` claims the external orders of the `[trade]` instruments (`external_order_instrument_ids`), after any it declares, and no other instrument the strategy reads: a strategy returns its config's claims from `Strategy::external_order_instrument_ids`, as `EmaCross` and `ModelEma` do, Nautilus' default returning none, and the live node registers them as it adds the strategy (see [live](../live/README.md)).

`[data].series` is exactly what `Part::reads` says the strategy reads: missing, extra and duplicate series are errors. The EMA reads only the first bars series of its traded instrument. `[trade].instruments` lists each instrument traded by its `instrument_id` alone: no instrument has a size of its own, and a `trade_size` is refused as the config is read, at its value, pointing to `[trade].risk`. `[trade].risk` is the fraction of equity a trade risks at the config's stake, written as a percentage (`"0.5%"`) above 0% and below 100%; a bare number is refused, as it could be a fraction or a percentage. A strategy that does not size its trades by risk, one holding a target exposure such as a rebalancer keeping target weights, declares `Part::SIZES_BY_RISK` false: its `[trade]` takes no `risk`, which is refused as an unknown key, and `config.stake()` panics, as `config.model()` does for a strategy without a model. It sizes its orders itself through the plain Nautilus API (`portfolio().equity`, its positions from `cache()`, `order().market`, `submit_order`), not through `orders::Trade`. Every other strategy keeps the default and requires `risk`; a model strategy must, its model being priced at the reference stake. When no series prices a traded instrument (its bars, quotes or trades), its quotes are added to data requirements for execution, not to `[data].series`: Nautilus prices a market order from quotes, trades or external bars, so depth, book deltas or custom data alone would have its orders denied. Consumers use `data_requirements()` rather than reconstructing requirements from config. `[trade].conversions`, optional, lists the FX pairs the equity a trade is sized from is converted through into the traded instrument's P&L currency, by their instrument ids, all on one venue: `conversions = ["EURUSD.ICMARKETS"]` for an IC Markets account in EUR trading gold quoted in USD. Each pair is added to the data requirements in one form, the first its venue's history serves (`venues::serves`) of its own 1-minute BID and ASK bars, then its quotes (`venues::rate_series`), so fill-catalog fills it, a backtest replays it and a live warmup requests it, and a backtest reads the rate a live run reads. Bars come first: a rate needs one recent value, and bars are the lighter history. So an IB pair is read as its bars (`EUR/USD.IDEALPRO-1-MINUTE-BID-EXTERNAL` and `-ASK-EXTERNAL`), to the bar types; a cTrader pair as its quotes, to the ticks, as a traded instrument's are, cTrader's history being quotes alone. The strategy subscribes to a pair's bars as to any bar type of the requirements, so its `on_bar` gets them beside its own and decides on its own alone: the EMA's signal counts its traded instrument's bars only (see [orders and positions](#orders-and-positions)). Left out, nothing is converted and the requirements are as before.

Declare each indicator name and argument type in `Part::INDICATORS`, build it from `config.indicators`, and register it for its input. Indicator tables not declared by the strategy are rejected. The shared config validates the declared arguments and strategy rules. A model strategy's features are declared the same way; its code hands each feature's table to the feature set rather than building it, and the TOML marks no role (see the [model guide](../model/README.md)). An argument type is `Deserialize` and `Serialize`, since a feature's arguments enter the fingerprint.

Bars are time-aggregated internal bars; `from` makes them composite from external source bars. Internal source bars are rejected because live warmup cannot request them. Tick series may be quotes, trades, book depth, book deltas or instrument-keyed custom data, which no fill-catalog source supplies and no live client streams, so a live run reading it is refused before anything connects (see [live](../live/README.md#startup-and-routing)). A book comes in its venue's format, the one its live data streams (`venues::book_format`), in a backtest as live, and is subscribed in it (`strategy::subscriptions`): its deltas at its book type, asking no depth, so each client streams the whole book it gives, its depth at its levels; a replay subscribes so too, though it reads neither from a subscription that manages no book. Deltas of an L3 book (L3_MBO) are orders, each added, changed or removed by its id, as LSE gives a `GLBX` contract's or an `XNAS` stock's; deltas of an L2 book (L2_MBP) are no orders: OKX's are price levels, each a level's new size, and IB's the rows of its market depth, each by its position, and by the exchange posting it on SMART depth, an update able to move a row to another price; so a feature reading deltas reads orders on one venue, levels or rows on another, and is not portable across venues as is. Depth snapshots hold the levels a side their venue sends, ten on LSE and five on OKX; IB streams no depth, and a cTrader broker no book. Custom data of no instrument, such as an LSE reference series, is not a tick series: `[data].custom` lists it, each entry a Nautilus data type, its `type_name`, its `identifier` and its `metadata`, as `DataType::try_new` takes them, `{ type_name = "LseRow", identifier = "US10Y", metadata = { source = "bond_yields", symbol = "US10Y" } }` for LSE's daily 10-year US yield. The identifier is the config's to choose and required: it keys the series in the catalog (`data/custom/<type_name>/<identifier>`), where Nautilus writes a fill's rows and a backtest reads them, so without one every series of a type would share one path; a config naming rows already stored writes the identifier they are stored under. The metadata says what the type's source asks for, LSE's a `source` and a `symbol` alone, which its client checks (see [the adapter's reference rows](../../crates/lse/README.md#reference-rows)). An entry is refused as the TOML is read if it has an unknown key (Nautilus' own `DataType` deserializer would take a `topic`), no identifier, or an identifier inside its metadata, which Nautilus reserves; and at validation, under `data.custom[i]`, if its identifier holds a backslash, which Nautilus' catalog writes as a folder separator and reads back as a character, so the series would be stored where no read finds it, or keys no catalog folder of its own, empty, blank or slashes alone once made the folder Nautilus names, `/` removed and `^` made `_` (both under `data.custom[i].identifier`), if an entry before it of its type is stored under the same folder (`US/10Y` beside `US10Y`), whatever its metadata, or if no source serves its type or its metadata (`venues::serves_custom`). No `Part::reads` answers it, so a strategy lists it beside its series; its subscriptions subscribe to its data type at their start (`strategy::subscriptions`), and its `on_data` gets the rows without the strategy subscribing itself. Data requirements carry it apart (`DataRequirements::custom`), each data type as the config gives it, in a fill, a replay and live alike: fill-catalog fills it from its type's source, LSE's rows from LSE, and a backtest replays it over its window, each row when its values are known (a date's at its end), registering the sources' types itself; a live warmup would request it of its source's client, catalog first, but a live run reading any its source does not stream is refused before anything connects (`venues::streams_custom`), and LSE streams none. Other custom types must be registered before catalog replay. The strategy subscribes to its own tick and book streams. Consult the [catalog guide](../catalog/README.md) for source availability and [backtest guide](../backtest/README.md) for replay.

A futures root's bars must be internal LAST bars built from its trades; orders must name a contract, not a root. Root tick subscriptions and continuous bars require roll handling; see [rolls](../rolls/README.md) for calendars and transitions. A conversion pair's quotes on a root need none: a futures contract has no base currency, so Nautilus' rates leave it out, rolled or not (see [Orders and positions](#orders-and-positions)), and the EMA, whose only ticks are its pairs' quotes, holds no roller.

## Bars and sessions

Internal BID, ASK and MID bars are built from quotes, LAST bars from trades. A bar stamped at close contains ticks in `(open, close]`; quote-bar volume sums quoted sizes, not trades. LAST bars carry no spread. Composite bars aggregate source bars, so their high and low reflect those source intervals. Backtest and live disable empty time bars: a period without a tick or source bar produces no bar rather than a stale flat bar.

A configured session accepts a bar only when its whole span lies within the local day's open and close in the configured IANA time zone. Outside bars neither update indicators nor trigger orders, including during warmup. Omit the session for 24/7 trading; `00:00`–`23:59` excludes the bar closing at midnight. Sessions are rejected with composite bars: composite bars are built and stamped five seconds after close to allow source bars to arrive live, in a backtest and a dataset run as live. Quote-built bars have no such delay, unless the strategy also reads composite bars: the delay is the data engine's, for every time bar it builds.

## Orders and positions

A trade is built without a quantity: `Trade::new` takes its instrument, side, exits, the reference price its exits are set from, and one R, the distance in price from that reference to its stop, or an ATR for a trade ended by its time alone. Its fields are the order module's, so no other code changes its exits or its one R once it is built. A strategy owns how much it risks: the stake, the config's risk times a multiple, 1 at `config.stake()`, scaled by `stake.times(k)` for a positive `k`. `trade.send(strategy, stake, rates)` reads the equity of the account its orders are checked against as its broker reports it (see below), converts it into the instrument's P&L currency at `rates`, the config's (`config.rates()`), and sizes the trade with Nautilus' `calculate_fixed_risk_position_size`: the stake's fraction of that equity over what its stop is worth on one unit, rounded down to the instrument's size increment and capped at its maximum quantity, no commission counted. The stop it is sized at is one R from the reference on the instrument's tick grid, rounded away from the reference, so a size never risks more than its stake. A size rounding down to zero sends nothing and logs a warning; an equity the rates do not convert, holding a currency no listed pair reaches or with no rate cached yet, sends nothing and logs an error. Nautilus' risk engine judges what is sent: a quantity below the instrument's minimum, or a margin beyond the free balance, is denied, and the run goes on. Each entry is tagged with its R in money, its quantity's worth over one R (`R:500.00 USD`), and its stake's multiple (`MULTIPLE:2`), read back with `orders::entry_risk`. Inverse instruments are refused at start, since the sizer reads a P&L as a multiple of a distance in price. A model strategy sends its decision's trade the same way, at a stake and rates of its own (`decision.trade().send(self, stake, rates)`); its model is priced at the reference stake, the config's risk of the dataset balance converted at the decision's rate, through `trade.send_at(strategy, stake, equity, ids)`, which sizes at a fixed equity in place of the account's (see [model strategies](../model/README.md#reference-stake-and-the-strategys-stake)).

The account is the one Nautilus' risk engine checks the orders against (Nautilus' execution guide, `concepts/execution`, "Account selection"): the account the cache registers for the execution client routed for the instrument's venue, else for the default client (`Cache::client_id_for_venue`, then `Cache::account_id_for_client`), else the account issued under the instrument's venue. A live node routes each cTrader broker's venue and OKX to their own clients and makes IB the default client; a backtest routes each simulated venue to its own. IB's account is issued under `IB`, not the exchanges its instruments name (`IBIS`, `IDEALPRO`), and is found through IB's client. The equity is the account's balance plus the open P&L of its positions on the instrument's venue: positions the same account holds on its broker's other venues are left out, as are other processes', which the cache does not hold anyway, one process running one strategy; live on IB, the equity is the account's net liquidation, which counts every position of the account, on any venue and of any process. Where it is read from is its broker's answer in the venues table (`venues::equity_source`): the strategy's portfolio (`Portfolio::equity`, which adds the open P&L to a margin account's balance) for a cTrader broker, OKX and a backtest's simulated account, whose balances leave open positions out; the account's balance totals alone on IB, whose net liquidation holds that P&L already (see [IB](../venues/ib/README.md#trading-and-warmup)). An account with a base currency, a cTrader account's, reports its equity in that currency alone, which the trade converts. An account without one, OKX's, holds each currency apart, its balance in one and a position's open P&L in another: the trade converts each and sizes on their sum, not on the open P&L alone, a loss counting against the balance.

Conversion (`strategy::conversions`) reads Nautilus' own rates. Each non-zero amount of the equity is converted at Nautilus' cached rate on the pairs' venue, `Cache::get_xrate(venue, from, to, PriceType::Mid)`, the mid of the latest quote of each pair on the path Nautilus finds through the venue's pairs, or of the closes of its latest BID and ASK bars for a pair with no quote cached, an IB pair's, as Nautilus' portfolio converts, and the amounts are summed; an amount of zero needs no rate, so an empty balance or a flat P&L in a currency no pair reaches blocks no trade; Nautilus' fixed-risk sizer then takes the converted equity at an exchange rate of 1, since its own rate converts one amount and an equity may hold several currencies. The entry's R tag stays in the P&L currency. Without conversions, an amount in another currency than the P&L's is not converted. Before a pair's first quote or bars are cached there is no rate through it, so a decision then sends nothing; a live strategy subscribes to the pairs at its start (see [live](../live/README.md#fx-conversions)). The pairs of a broker whose account has a base currency are on the traded instrument's venue (see below); those of one whose account has none, IB's, may be on any one venue, only the sizer converting: gold on GLBX, which lists no FX pairs, traded through IB on an account in EUR converts through `conversions = ["EUR/USD.IDEALPRO"]` live, its backtest taking a balance in USD (see below). A model strategy's dataset balance is converted the same way, at each decision's rate, and refused by the check a backtest's balance passes (see below and [model strategies](../model/README.md#reference-stake-and-the-strategys-stake)).

A config whose conversions can never work is refused before a run, naming why. The config's load refuses a pair whose venue's history serves neither its 1-minute BID and ASK bars nor its quotes, an OKX pair, naming the pair and its venue, since no rate of it could be read; pairs on more than one venue, naming the venues, since a strategy converts at Nautilus' rates on one venue, its pairs'; for an instrument traded whose broker's account has a base currency (a cTrader broker's, `venues::has_base_currency`), a pair on another venue than the instrument's, naming both, since Nautilus converts that account's margins, commissions and P&L into its base currency only through rates on the traded instrument's venue, while for an account without one (IB's, OKX's) only the sizer converts, so the pairs may be on any one venue; and pairs listed by a strategy not sizing its trades by risk, which sizes no trade from equity, `conversions` being refused as an unknown key as its `risk` is. A backtest refuses before its run, reading the definitions in its catalog, a listed pair whose definition has no base currency, naming the pair, since Nautilus' rates leave such an instrument out, and a balance whose currency the pairs do not reach a traded instrument's P&L currency from, naming both currencies. On a broker whose account has no base currency (IB's, OKX's) it refuses too a balance in another currency than a traded instrument's P&L currency, naming the instrument, its venue and both currencies, since Nautilus books such a simulated account's losses and commissions only in a currency it holds, a limitation no upstream issue tracks (see [backtesting](../backtest/README.md#leverage-and-venues)); a model's dataset balance is not refused so, its dataset runs booking nothing, nor is a live run. A live run has no definitions before it connects: there a currency the pairs do not reach is a trade not sent, logged.

A trade's exits hold a `Bracket`, its take profit and stop loss, which produces a Nautilus bracket, or none, which produces a market entry. The time limit starts at send, not fill. Forward time events to `orders::on_time_event` and call `orders::arm_open_trades` on start so cached open trades regain their alerts after a restart. The alert cancels open orders and closes any remaining position; a partial exit does not end the remaining trade.

Leave `oms_type` unset so positions follow the venue. On a netting venue overlapping trades share a position and one trade's time exit closes the whole position, including the other trades' share. On a hedging venue each trade has its own position. The EMA is an example and permits overlap. Its bracket legs and time close are reduce-only except on IB, whose execution client denies them. On IB the two legs of a bracket share an IB OCA group instead, named after the entry and tagged on them besides Nautilus' own tags (`venues::bracket_exits_tag`), so IB reduces the other leg at a partial fill and cancels it at a full one even while the node is down; see [IB](../venues/ib/README.md#trading-and-warmup) for the group's type and what overlap still risks there, and [backtest](../backtest/README.md) for execution limitations.

## Warmup

Live requests history at start and hydrates indicators before the live stream. A backtest requests no warmup: it replays only its requested interval, and indicators initialize on that replay. Start earlier if decisions are needed at a particular time. A dataset build replays the features' warmup before its first day and stores no earlier decisions; see the [model guide](../model/README.md).

`strategy::warmup::Warmup` owns the request protocol, and `strategy::subscriptions` the subscriptions, which start at the time the warmup's start returns, where its requests end. It requests the history of every series of the data requirements its venue's history serves (`venues::serves`, the rule fill-catalog checks its series by): a composite bar requests its external source bars, other bars the quotes or trades from which they are built, and each tick series is requested as it is, whatever reads it, a feature, a conversion pair's rate or a traded instrument's prices. Nautilus caches the quotes and bars of each response, so a pair has its rate at the start, a start while the market is closed included if the warmup reaches back to its close. A series its venue's history does not serve, an OKX instrument's quotes, is requested no history: the warmup logs a warning naming why, and the series, subscribed from the start as every series is, and the bars built from it start there; a series its venue's live data does not stream is refused before the node starts (see [live](../live/README.md#startup-and-routing)). Custom data of an instrument is requested from the catalog alone. First, the warmup asks the definition of each instrument of the series that the cache lacks, of the client the venue's row names (its broker's, else its live data source's): the catalog answers first, so `LSEDGE` definitions, which LSE does not publish, come from there, and those the broker clients already cached are left as they are. Every series is asked in windows of 23 hours through Nautilus' time-range requests, each answered and written back on its own, and a run of empty windows does not end one. A window of book deltas whose UTC day's start the catalog holds, earlier windows' write-back included, is read from there and opens with a snapshot of the book at its own start, rebuilt at the book type of its venue's format, as the live stream that follows it is subscribed, so a feature reading deltas sees one per window beside the day's. When a request completes, it feeds the bars it built to indicators in chronological order, each once, composite bars included. It keeps the subscription continuous across the request boundary and sizes the live cache for the requested bars. Root continuous bars have a separate path; live currently refuses them, as described in [rolls](../rolls/README.md).

A completed request does not itself enable decisions: indicator initialization does. A model strategy's decisions also wait for every warmup request to complete, as features reading ticks can be initialized on the older windows alone. Live ticks start at the subscription, while older windows are still being answered, and Nautilus holds them for its bar aggregators alone: the warmup hands a model strategy's features the quotes and trades of its responses, holds the live ones until the last window is answered, then hands them over in the order they came, dropping those the history holds; each feature reads those of its own series alone, so a pair's or a traded instrument's quotes no feature reads reach none. Historical callback errors are logged rather than stopping the run, and an unanswered request leaves its group unfinished. The catalog supplies available history and the live client supplies missing intervals where supported; see [live](../live/README.md) for operational details. Recursive indicators retain a decaying dependence on their initial state even after initialization; allow several periods of history when reproducibility matters.
