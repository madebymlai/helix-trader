# Catalog fills

`fill-catalog` loads the instruments and source series required by the strategy into a Nautilus Parquet catalog. Strategy requirements and bar authoring belong to [strategy](../strategy/README.md); contract transitions belong to [rolls](../rolls/README.md). The backtest consumes the catalog as described in [backtest](../backtest/README.md).

The instrument venue selects the source of its definitions and of its history, each a part of its row in the [routing table](../venues/mod.rs): one source gives both, [OKX](../venues/okx/README.md) for `OKX`, [Databento](../venues/databento/README.md) for `GLBX`, [IC Markets](../venues/ic/README.md) for `ICMARKETS`, [Pepperstone](../venues/pepperstone/README.md) for `PEPPERSTONE`, and [IB](../venues/ib/README.md) for other venues, but for `LSEDGE`, whose definitions are the catalog's alone, written by hand, and whose history is [LSE](../venues/lse/README.md)'s. Custom data of no instrument, such as an LSE reference series (`DataRequirements::custom`), has no venue: its type names its source, LSE's rows (`lse::LseRow`) LSE, and no other type is filled. A run may use several sources: `venues::fill_history` gives each its instruments and runs the node's fill, then IB's. Definitions and the source series, not the internally aggregated strategy bars, are stored.

## Fill paths

Databento, the cTrader brokers, OKX and LSE answer historical requests through a Nautilus node. Each request names the client that answers it, which Nautilus' data engine routes by before any venue route, so the node's clients take no venue routes and two sources of one venue can share the node. The data engine answers a definition request from the catalog before asking the client; LSE, which publishes no definitions, fails the definition request of an instrument the catalog does not define, naming it. The node requests missing intervals sequentially and writes completed responses back. It waits for each answer with no deadline, as Nautilus requests have none: each client answers every request, a failed one with its failure, and a client that never answered would leave the fill waiting until interrupted. An answer its client does not report complete is counted as answered and written nowhere: its window stays missing and the next run asks for it again. LSE answers so a window reaching into the days it has not loaded yet (see [LSE history](../venues/lse/README.md)). IB uses the direct `fill_catalog` writer: its client returns payloads without the completed response envelope required for node writeback (nautilus_trader#5472). A failed request stops the fill; previously written data remains.

Each series request is one Nautilus time-range request (`time_range_generator`): the data engine asks for inclusive windows of the source's period one at a time, each ending at a multiple of the period from the request's start and the next starting 1 ns later, and writes each back on its own; adapters page within a window. `durations_seconds` repeats the period once per window, because Nautilus moves to the next duration after an empty window and ends the request, reporting success, when they run out. The request's last envelope is empty by design, so Nautilus logs one empty-response warning as each request ends. A definition precedes its series. Custom data of no instrument has no definition and is asked whole, as Nautilus' time-range pipeline windows no custom data request; Nautilus writes it back as custom data under its type and its data type's identifier. An empty answer may record coverage when adjacent to stored data; an isolated empty window records nothing and is requested again. A wholly empty first fill is not an error.

The direct writer resumes each series 1 ns after its stored end, even if the requested start is later, to avoid a gap. It refuses a start before the stored range: use a new catalog to extend backwards. An empty first response is an error; an empty resumed response writes no coverage and is requested again. Data is sorted and deduplicated by `ts_init` before writing. Windows are inclusive, and overlapping catalog intervals are invalid.

**Coverage is not completeness.** A nonempty answer can mark the entire requested window covered even if the source had only part of it. Check source history depth and availability before relying on a catalog; a rerun will not necessarily retrieve missing observations inside covered windows.

## Instrument identity

The source, catalog, strategy and live broker must agree on instrument IDs. IB keeps the venue of an instrument it loads by ID, so a contract the config names under Databento's venue (`ESZ21.GLBX`) keeps it live; only a contract IB has not loaded takes its exchange's venue (`ESZ21.CME`, Nautilus' `determine_venue`). Changing source or venue requires matching config IDs and a refilled catalog.

## Tests

Catalog fill tests are in `src/catalog` and `tests/node_fill`; venue-specific test gates are in the linked venue READMEs. They do not establish completeness of a remote source.
