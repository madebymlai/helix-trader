# Model strategies

Read the [strategy guide](../strategy/README.md) first for config, series, orders, bars and warmup. [`model_ema/`](../strategy/model_ema/) and [`config/model_ema.toml`](../../config/model_ema.toml) show a model strategy. For operation see [backtest](../backtest/README.md), [live](../live/README.md) and [rolls](../rolls/README.md).

## Authoring and decisions

A model strategy's `Part` sets `TAKES_MODEL`, builds the shared `FeatureSet` through `ModelPart::features`, and delegates `Part::reads` to `model::reads`. Implement `ModelStrategy`: `blueprint` builds the model from config, and `with_blueprint` constructs `ModelHandle::new(&blueprint, mode)` for each mode. The handle decides; it does not submit orders. Register the strategy in `main.rs` for dataset, train, backtest and live.

The validated blueprint owns the strategy ID, features, model config and data requirements; venue and paths remain separate. It computes one fingerprint for the dataset and stores on a venue. Each strategy and dataset replay needs fresh mutable features. See [`blueprint.rs`](blueprint.rs) for construction and validation.

### Features and data

Build an ordered `FeatureSet` with sources, feature-code version and warmup. Indicator features are built from declared tables: code chooses membership and series, while the tables supply arguments and cannot add or remove features. A table feeding one feature names it; one feeding several produces `<series>:<table>`. Custom-data features keep their code-given names. A feature is a Nautilus indicator exposing `Feature::value`; built-in moving averages do so, while a custom indicator supplies its argument type. See `FeatureSetBuilder` in [`features.rs`](features.rs) for builders and naming.

An `over_bracket` quote feature reads the decision's bracket width, cadence and limit, sharing the target setter's ATR so its width matches the decision's target. Declared features and target ATR determine the series checked against config; traded-instrument quotes added by shared data requirements are not extra declared series.

Nautilus registers the set for bars; quotes and trades reach it through warmup. Live ticks are held until the last warmup response, then delivered in arrival order, dropping ticks already covered by history by event time within each series. This compensates for Nautilus holding live ticks for bar aggregators but not actor indicators (issue #16). `model_data_hooks!` forwards historical responses including book depth, deltas and custom data, and live quotes and trades; warmup-built bars reach features too. **Live or replayed book depth, deltas and custom data are not forwarded to features:** such a feature would see only live warmup data.

### Cadence and decision

The cadence is epoch-aligned and fires after the shared bar-build delay plus a small margin. Composite bars cause a five-second delay in every mode, including dataset and backtest; otherwise there is no build delay. See [strategy](../strategy/README.md) for bar handling. Decisions require fresh market data of the traded instrument since the previous grid point: custom data or another instrument's activity is insufficient. Cold features or stale data produce no row or trade. Root tick features reset on a roll and must initialize on the new contract; see [rolls](../rolls/README.md).

The handle uses the latest valid pair of enabled sides from the same train and valid-from time; a one-sided strategy has a one-side pair. It never mixes or uses a partial pair. Live decisions wait for all warmup requests. The handle gates on initialized features and target ATR itself, so the strategy needs no redundant gate. Each side reads strategy features followed by that side's target payoff features and predicts R. The pair jointly calibrates its level `C` and side call `D`; one side uses a level line alone. See `Ksplit` in [`calibration.rs`](calibration.rs) for the equations. Each side's calibrated expected R times its own unit is expected net money. Live, meta replay, holdout and walk-forward scores share this decision path. A side must clear its margin; the higher expectation wins and ties yield no trade. A negative expectation cannot clear a zero margin even for a tiny unit.

**An in-market stop can still be traded:** on Nautilus' simulated venue the stop is rejected, leaving the position unprotected until take profit or time limit, and the trade has no dataset row. No valid pair, cold or zero ATR, or an exit rounded to the reference price yields no trade. The target is set before model selection, so a missing instrument is an error even without a valid model.

Send `decision.trade()` through `strategy::orders`; dataset targets use the same trade path. Changing its instrument, size, exits or holding time invalidates the holdout and expected P&L economics. Forward order and time events to the handle, time events first to the order module, and rearm open trades on start. IB exits and time closes are not reduce-only, in datasets as live; see [IB](../venues/ib/README.md#trading-and-warmup).

## Targets and datasets

A strategy has one `[model]` target: either a bracket with both take profit and stop, or a time-only trade. Time-only requires its own ATR beside the limit; a bracket owns its ATR and cannot have a redundant ATR beside it. ATR must warm within warmup. A lone exit or an exit beside the limit is rejected. Read prices from the decision. `Target` and `TargetConfig::validate` in [`targets.rs`](targets.rs) give the configuration shapes and validation details.

A dataset run opens long and short target trades at each decision on a simulated hedging venue. Exits may mix basis-point and ATR distances and are rounded to the nearest tick; a bracket's ATR argument table is allowed only when an ATR distance is used. ATR bars derive from the traded instrument's declared inputs at the decision cadence. Cold or zero ATR, no reference price, or an exit rounded to the reference price leaves the target unsettled; dataset runs log the reason, while live decisions suppress it. A missing instrument errors before orders. Inverse instruments and commissions in a currency other than instrument P&L currency fail dataset startup and error at live decisions: no currency conversion is performed. See [`targets.rs`](targets.rs) for order IDs and target mechanics.

One commission setting drives simulated backtest fees, dataset targets and live store settings: fixed, rate or per-quantity. Thus the same trade uses the same economics. See [backtest](../backtest/README.md) for fee options and rounding.

The target appends each side's payoff features to the strategy features without declaration; the meta model reads strategy features without them. Brackets include take-profit R and nominal stop loss before overshoot; every target includes entry cost. They account for spread and commission relative to each side's unit: long enters at ask, short at bid; trades or bars without quotes have no spread. See `PayoffFeature` and `TargetSetter::payoff` in [`targets.rs`](targets.rs) for payoff names and formulas.

A row is self-contained: features and times plus each side's payoff, net P&L, commission, exit and unit. A payoff width mismatch is an error; `DatasetRow` in [`dataset.rs`](dataset.rs) specifies the columns. Unit is exact, unrounded quantity × multiplier × distance in P&L currency: stop distance for brackets, ATR distance for time-only. Sub-cent units are valid; realised R is P&L divided by unit. A row settles only after both sides close. Denied, rejected or unfilled entries, an in-market rejected stop, or positions still open at run end leave no row; inspect logs rather than assuming a row per decision. Bars-only fills are optimistic, including high before low; see [backtest](../backtest/README.md).

Datasets are keyed by strategy and fingerprint and stored by day. A build replays from feature warmup before the first missing day through the target limit after the last, storing only requested decision days. Supply prior history in the catalog: replay does not check or request it. Recursive features such as EMA or Wilder ATR never entirely forget their start; roughly 5–10 times the longest recursive period makes dependence negligible, not bit-identical. Running sums can also differ in their last bits.

Rebuilding deletes covered day files before writing because the catalog skips existing files. Do not consolidate the dataset directory: that loses day intervals. A train at `t` uses decisions before `t` settled by `t`; incomplete days are replayed to `t` and not cached complete. Concurrent builders can race on day files and manifest. Do not backtest against a catalog and store a live node is retraining into simultaneously.

## Training and acceptance

Each enabled side regresses realised net R. The window ending at `t` has a final holdout preceded by an equally long calibration interval. Fit on earlier rows settled by calibration start, calibrate on calibration rows settled by holdout start, and judge holdout rows settled by `t`. This purging prevents leakage, and the target limit separates window decisions from first model use. The limit must be shorter than cadence and both training and meta windows; the training window must leave fitting room before calibration and holdout. The cadence constraint also prevents overlap in live netting accounts despite the hedging dataset venue.

The gate judges the handle's target trade, not later strategy filters. Enabled sides are fitted and accepted as a pair or not at all; failure of one keeps the current pair. Joint calibration fits level and side-call slopes clipped to `[0, 1.5]`; a two-sided pair ties when both sides' predictions are constant, and a one-sided model fits its level line alone. Each side needs positive squared-error skill against its own baseline, the mean R of its fitting and calibration rows. The economic gate picks among the new pair alone, once per holdout row before meta, never mixing an older side. Aggregate picks must meet `min_trades` and `min_pnl`, and net P&L per trade must exceed the all-side-trades baseline.

Mean `R - E'`, calibration slope and top-decile gap are diagnostics, not gates; `ExpectedScore` in [`score.rs`](score.rs) defines these and skill. The same picks at 1.5 times commission are a stress report, not reselection. Accepted models publish as judged without refitting; failure reports the pair reason alongside per-side metrics, and manifests carry pair calibration identity. See the training and publication reporting in [`train.rs`](train.rs) and `ModelManifest` in [`store.rs`](store.rs) for first-refusal order, pair earnings and side scores. Publication is a rename per side, **not an atomic pair**: a failure or crash between renames can leave an orphan, which is unusable and fitted again with its pair on the next train.

### Scores

Backtest scores use the same pair decision path: each picked trade counts once for its side before meta, ties count for neither, and partial pairs cannot decide. Each side's all-trades baseline and prediction metrics cover all eligible rows with its model. Meta prediction metrics cover all rows with a side pick and a valid meta model; meta earnings count trades passing its money margin, expected R times the picked side's unit. Scores at 1.5 times commission use the same picks. These figures describe target decisions, not necessarily the actual strategy report if it filters them. Models and their own persisted fitting-and-calibration mean R baselines are scored on the same rows; failed checks exclude the pair and retain the current model. This applies even to off-grid publications or refused retrains.

### Meta-labeling

Side models are the primary decision; a meta model can filter their chosen trade for any target, not replace them with a rule primary. The strategy may ask the model only when its own signal fires at cadence. Historical meta rows use the pair valid at each decision, out of sample, and exclude decisions with no pick. They contain strategy features, picked side and calibrated `C'` and `D'`, not target payoff features. The meta regresses the picked trade's net R and fits its own one-sided calibration line. It takes the unchanged target size when calibrated expected R times the chosen unit is at least its money margin. Its own holdout requires positive skill, minimum trades and P&L, and better P&L per trade than all its trades. Missing valid meta or NaN expectation means no trade. Legacy probability `threshold` and meta `size` are rejected; use margin and target size.

### Scheduling

With periodic retraining, a train at `t` keeps models valid exactly at `t` and fits missing ones, both sides together. A meta waits if no side pair was valid before `t`; its earliest row is the first pair. The train replays once from the earliest needed fit, or not at all if nothing needs fitting. It exits successfully when all models are published or in use; failed, refused or waiting models produce a nonzero exit. A backtest builds from its first plan's earliest needed replay (or first train time if no fit), trains only when needed, and scores in retrain periods. See [backtest](../backtest/README.md) for operation.

Omit `retrain` for a never-retrained strategy; if present, the interval must be positive. At `t`, the latest pair and meta valid at or before `t` stay in use; an orphan is not a pair. If sides exist, a missing meta fits alone. With neither pair nor meta, one replay fits, calibrates and judges sides as of `t` minus the meta window using rows settled by that earlier time, then fits meta at `t` on those same sides' out-of-sample decisions. If sides fail, meta waits. Periodic training does not perform this two-time fit.

A never-retrained backtest trains missing models only at its start, then reuses them. It refuses to run without a pair and configured meta at start; a periodic backtest can run even if all trains are refused. Its scores cover one period using each model's own baseline; with models already in use it builds only the span's days. Live never-retrained strategies have no retrain actor, timer or launched train; externally published models are picked up at the next decision, subject to the usual bar delay. See [live](../live/README.md) for retrain operations.

## Store, validity and versions

The dataset fingerprint includes ordered feature names and sources, normalized parsed feature-table arguments, feature version and warmup, decision rule and nonzero bar-build delay, target and ATR inputs, dataset version, and normalized venue costs, balance and leverage. Indicator tables used only by strategy logic are excluded. Model stores also key learner, retrain interval, window, holdout, acceptance minimums, both side margins and `store::VERSION`; meta includes the sides' interval. Never-retrained stores are partitioned from periodic ones. Changing these selects different data or models rather than silently reusing incompatible results.

`ModelSet` owns the side and meta stores, schemas, fingerprint and valid-from listings, including the historical store used for meta rows. A pair's valid-from requires all enabled sides at that time. A published model is written by rename. An unreadable store fails handle construction. At each decision the handle lists stores again and swaps to the latest valid pair and meta at that boundary. A failed listing logs and retains **all** previous lists; a model already listed can still swap in.

Before use, the handle checks fingerprint, ordered feature names and width, and reproduces stored raw pre-calibration prediction probes bit for bit. Each side must carry the same calibration identifying its pair, valid-from and sides; meta carries its own. A failed side check refuses the whole pair and retains the current one. With no valid pair, no side trades.

Bump the strategy's feature version when feature computation changes without a corresponding name, warmup or config change. Changed table arguments are already keyed; a value-preserving rename or refactor needs no bump. Bump `store::VERSION` for model file, manifest or read-format changes: models retrain, but datasets remain. Bump `dataset::VERSION` for shared row-producing changes, including Nautilus indicator, matching or fill changes, or dataset manifest changes. When rows or their version are affected, update and commit the golden snapshot with the version:

```sh
GOLDEN_ROWS=write cargo test --test backtest backtest_golden_rows::
```
