# Model strategies

Read the [strategy guide](../strategy/README.md) first for config, series, orders, bars and warmup. [`model_ema/`](../strategy/model_ema/) and [`config/model_ema.toml`](../../config/model_ema.toml) show a model strategy. [`model_cross/`](../strategy/model_cross/) and [`config/model_cross.toml`](../../config/model_cross.toml) show one with an event filter. For operation see [backtest](../backtest/README.md), [live](../live/README.md) and [rolls](../rolls/README.md).

## Authoring and decisions

A model strategy's `Part` sets `TAKES_MODEL`, builds the shared `FeatureSet` through `ModelPart::features`, and delegates `Part::reads` to `model::reads`. Implement `ModelStrategy`: `blueprint` builds the model from config, and `with_blueprint` constructs `ModelHandle::new(&blueprint, &mode)` for each mode. The handle decides; it does not submit orders. Register the strategy in `main.rs` for dataset, train, backtest and live.

The validated blueprint owns the strategy ID, features, model config and data requirements; paths remain separate. It computes one fingerprint for the dataset and stores, of the venue of the dataset runs the config declares (see [dataset venue](#targets-and-datasets)). Each strategy and dataset replay needs fresh mutable features. See [`blueprint.rs`](blueprint.rs) for construction and validation.

### Features and data

Build an ordered `FeatureSet` with sources, feature-code version and warmup. An indicator feature has one declaration, `FeatureSetBuilder::feature`, on the list of series it reads: any number of bar types, tick series (quotes, trades, depth or deltas) and custom series (`Series`), in any combination, on any instruments or futures roots, a single series being a list of one. It gets each update of any of its series once, through Nautilus' handler of the update's kind or, for custom data, its own (`Feature::custom_handler`, below), in the order Nautilus delivers it; an update no feature reads reaches none. Indicator features are built from declared tables: code chooses membership and series, while the tables supply arguments and cannot add or remove features. A table feeding one feature names it; one feeding several produces `<series>:<table>`, the series being the feature's whole list in the order declared, joined by a comma and a space. The fingerprint carries each feature's whole list, so adding, removing or reordering a series rebuilds the dataset and the models. The set's tick series, bar types and last updates (the freshness a decision reads) gather over every series of every feature, each once. A feature's series on a root read the front contract; a roll moves each of them to the post contract and resets the feature once, its series on other instruments staying as they are. Custom-data features keep their code-given names. A feature is a Nautilus indicator exposing `Feature::value`; built-in moving averages do so, while a custom indicator supplies its argument type. See `FeatureSetBuilder` in [`features.rs`](features.rs) for the declaration and naming.

A set may declare one event filter beside its features, `FeatureSetBuilder::event_filter`, on its list of series and from its `[indicators.<name>]` table as a feature is declared: an indicator implementing `EventFilter::is_event(previous, now)`, which says whether the decision at `now` is an event, `previous` being the grid point before it (see [Cadence and decision](#cadence-and-decision)). An event filter of time alone, a session, reads no series. Its series join the set's tick series, bar types and custom series, each once, and so are subscribed, warmed live, reset at a roll of their root and checked against `[data].series` as a feature's; on a custom series it needs a handler of its own (`EventFilter::custom_handler`), and it may be formed over the bracket as a feature can (`EventFilter::over_bracket`). It is never a model input: its name and value are in neither the feature vector nor the dataset's feature columns, and a feature from the same table keeps its name. Declare the same indicator as a feature too for the model to read it. The fingerprint carries its table, arguments and series, so changing them rebuilds the dataset and the models; an indicator table only the strategy's own logic reads stays out of it. The build refuses a second event filter and one on a custom series it has no handler for, naming each. [`model_cross/`](../strategy/model_cross/) is the example: `model_ema`'s features, deciding only at the grid ticks after a cross of two simple averages of the traded instrument's bars, an edge filter (`cross.rs`).

Reading over the target's bracket is a property of the indicator, not of its declaration or a kind of series: a feature formed over it (`Feature::over_bracket`, declared on any list of series as any other) reads the decision's bracket width, cadence and limit from the width the builder takes once (`FeatureSetBuilder::bracket`), sharing the target setter's ATR so its width matches the decision's target. A set is refused when built if a feature over the bracket has no width, a width is given that no feature reads, or a second width is given; such an indicator panics, rather than reading NaN, on a width it was never handed. Declared features and target ATR determine the series checked against config; traded-instrument quotes added by shared data requirements are not extra declared series.

The set is registered with none of Nautilus' indicators: its bars, quotes and trades reach it through the warmup, as the target's ATR's bars reach the ATR. A live warmup hands a feature the history of all its series in time order across them, the bars its requests build among them window by window, as a replay does, through the warmup's merge of its series, which goes with helix-trader#46 (see the [strategy guide](../strategy/README.md#warmup)). Live ticks and bars are held until the last warmup response, then delivered in arrival order, dropping those already covered by history by event time within each series, a bar by its close. This compensates for Nautilus holding live ticks for bar aggregators but not actor indicators, and a bar aggregator's live data only until its own request completes (issue #16). `model_data_hooks!` forwards historical responses including book depth, deltas and custom data, and live bars (`on_bar`), quotes, trades, depth, deltas and custom data (`on_data`). Nautilus registers indicators for quotes, trades and bars only, so book depth and deltas reach features through the strategy's handlers (`on_book_depth`, `on_book_deltas`), held during a live warmup and deduplicated as quotes and trades are (issue #16 covers both). Nautilus' `Indicator` has no custom-data handler at all, and Nautilus hands custom data to the actor's `on_data` and `on_historical_data` alone, so a feature may list custom series among its series only if it gives a handler of its own (`Feature::custom_handler`, a `CustomHandler`); one without is refused when the set is built, naming the series. Such a feature gets each point once, in delivery order among its other series, live, replayed and from the warmup's responses, through the same hooks, held and deduplicated by event time within each data type as ticks are; a custom series on a root reads the front contract's data type and moves at a roll as its tick series do, resetting the feature once. Its custom series are among the set's custom series, and its fingerprint carries each one's whole data type, as a raw feature's does. A raw feature reads the latest point of its custom data type in Nautilus' cache, which the data engine fills with every custom data point it processes, live or replayed, before the strategy's handlers run; the data engine does not cache a request's response, so the warmup adds its own, leaving out any point no later than the latest the cache already holds, so that a live point taken while the request was pending stays the latest. A raw feature is of one kind: it reads a custom series, named whole, its type name, identifier and metadata (`FeatureSetBuilder::custom` over a `CustomSeries`), an instrument's custom data under its id among them: on a root (`GC.GLBX`) it reads the contract standing for the root, from its registration, and after a roll reads the post contract's latest point, its slot holding the root it reads as a tick feature's does; any other series stands for itself, and no roll moves it. Its fingerprint carries the series as the config names it, its data type's topic, the root's on a root, so pointing it at other data rebuilds the dataset and the models. The strategy reads each custom series its features read (`model::reads`), checked against `[data].series` both ways as any other series, whole, as the cache keys its points: one read and not listed is refused under `data.series`, one listed and read by no feature under `data.series[i]`, each named.

### Cadence and decision

The cadence is epoch-aligned and fires after the shared bar-build delay plus a small margin. Composite bars cause a five-second delay in every mode, including dataset and backtest; otherwise there is no build delay. See [strategy](../strategy/README.md) for bar handling. Decisions require fresh market data of the traded instrument since the previous grid point: custom data or another instrument's activity is insufficient. Then a strategy with an event filter decides only at the grid ticks it marks as events, its filter initialized; then every feature must be initialized. Stale data, a cold event filter, a tick that is no event or cold features produce no row, target, score or trade, so dataset, training, walk-forward and trading see the same decisions; a stale decision and one that is no event are logged at debug. In backtest and live execution, the model skips a new entry while its strategy has an outstanding order or open position on the traded instrument. A time limit schedules a close; it does not confirm a fill. Once the trade is clear, the next eligible decision can enter. Root tick features and the event filter reset on a roll and must initialize on the new contract; see [rolls](../rolls/README.md).

Choose when the model is asked by the event filter, and filter its answer afterwards only for account or execution state:

- Every market-based choice of when to trade, by time, session, regime or signal, is an event filter. Filtering the answer for a market reason has the model learn and be scored on decisions it never trades.
- Only account or execution state filters the model's answer afterwards: an open position, a loss limit, a venue down, the choice among several instruments' decisions.
- The delay from an event to its decision is at most one grid interval. A decision's time is its timer's scheduled time, the `TimeEvent`'s `ts_event` that the strategy hands `ModelHandle::decide` from `on_time_event`: a backtest's clock reads it in the callback, while a live clock reads later by however long the callback waited, which would leave gaps and overlaps between consecutive decisions. An edge filter (a cross, a sweep) keeps the `ts_init` of its last event and answers whether it lies after the previous grid point, the boundary freshness reads, and not after the decision's time, so consecutive decisions tile the grid: an event between two grid points makes the next decision and none is lost or counted twice, even one a live filter read before an earlier decision's callback ran. A session answers from the decision's time, and a regime from its own state. Pick the interval that delay fits.
- An event filter's answer must depend only on the data in its warmup and the grid, so that a backtest, whatever its start, marks the events its dataset days marked, each replayed from its own start; otherwise it trades at a tick with no dataset row. An indicator that remembers where its replay started, such as an exponential average, breaks this when its event turns on a gap smaller than what is left of that start: `model_cross` crosses simple averages, which read their last closes alone.

A finer grid costs its ticks that are no event, each still a timer event and a decision's checks: about 0.5 µs a tick, some 40 ms a day replayed at one second. Measured for `model_cross` at `decision = { every = "1m" }` and at `"1s"`, its config otherwise unchanged but for its target ATR's `bar_interval = "1h"` in both, so that neither sizes its stops on bars of the grid's length: a `train --from 2026-10-01 --to 2026-11-01`, training at five retrain times, the first window starting at 2026-04-04, then a `backtest` of that month, over the IC Markets catalog's XAUUSD and EURUSD quotes. A release build ran on an Intel Core i7-1365U laptop (12 threads, 30 GiB, Linux), logs at warn; each figure is the median of five trains or of ten backtests, the backtests timed once their 4 dataset days were built:

| Run                                                           | 1m grid                 | 1s grid                 |
| ------------------------------------------------------------- | ----------------------- | ----------------------- |
| Train over the span: wall, CPU, peak memory                   | 39.1 s, 46.1 s, 324 MiB | 48.6 s, 55.2 s, 321 MiB |
| The first train, 180 days built: wall, CPU                    | 30.2 s, 35.8 s          | 37.8 s, 43.2 s          |
| Backtest of the month: wall, CPU, peak memory                 | 5.6 s, 7.5 s, 259 MiB   | 7.0 s, 8.8 s, 269 MiB   |
| Dataset days built: first train, each later one, backtest     | 180; 8, 172 cached; 4   | the same                |
| Rows: each train's fit and calibration; the month's decisions | 78/26 to 65/39; 22      | the same                |

So one second takes about a quarter more time than one minute, in a dataset build as in a backtest, at the same memory. The month's decisions cleared no margin, so the backtest sent no order. Both grids gave the same rows, decisions and scores: the cross falls on its hourly bars' closes, a grid point of either, so the finer grid shortened no delay. A grid finer than the times its event filter's events can fall on decides at the same moments and only costs more; one second pays where an event can fall between them, a sweep or a burst of trades.

The handle uses the latest valid pair of enabled sides from the same train and valid-from time; a one-sided strategy has a one-side pair. It never mixes or uses a partial pair. Live decisions wait for all warmup requests. The handle checks the event filter, initialized features and target ATR itself, so the strategy needs no check of its own. Each side reads strategy features followed by that side's target payoff features and predicts R. The pair jointly calibrates its level `C` and side call `D`; one side uses a level line alone. See `Ksplit` in [`calibration.rs`](calibration.rs) for the equations. Live, meta replay and walk-forward scores share this decision path. A side trades when its calibrated expected R is at least its margin, written in R with its suffix (`margins = { long = "0.5R", short = "0.5R" }`); a bare number is refused at load, so an old margin in money is never read as R. The higher expected R wins and ties yield no trade, whatever the sides' units. See `R` in [`strategy/risk.rs`](../strategy/risk.rs).

**An in-market stop can still be traded:** on Nautilus' simulated venue the stop is rejected, leaving the position unprotected until take profit or time limit, and the trade has no dataset row. No valid pair, cold or zero ATR, an exit rounded to the reference price, or a size of none at the reference stake yields no trade. The target is set before model selection, so a missing instrument is an error even without a valid model.

### Reference stake and the strategy's stake

The model always works at one reference stake: the config's `[trade] risk`, multiple 1, of the dataset balance (`[model] dataset`) held as a constant equity, in the traded instrument's P&L currency. A balance in another currency is converted into it at each decision, by the conversion module a strategy's send converts the account's equity with (`Rates::convert`), at Nautilus' cached mid rate of the pairs of `[trade] conversions`, so a row's reference stake is of the balance at its decision's rate and a live decision's at the live rate; its unit stays in the P&L currency. Each target side is sized there with the same Nautilus function a strategy's send uses (`calculate_fixed_risk_position_size`, through `Trade::size`): the stake over its one R, the stop's distance for a bracket or the ATR for a time-only target, on the instrument's tick grid away from the reference price, rounded down to the size increment and capped at the maximum quantity. Its unit is that R in money on that size, and its payoff features are at that size. Dataset rows and the handle's live payoff features are priced the same way, and the handle reads no equity, so the model sees the same sizes in training and live whatever the account holds, whatever the dataset run's P&L, however the days were replayed, and whatever the strategy stakes. A side whose reference size rounds down to zero is no target: no row in a dataset run, no decision live. Converted, the reference size moves with the rate, as an account in the balance's currency sizes its trades: rows are in R, so what is proportional to the quantity cancels (price moves, the spread, rate and per-quantity commissions), and what remains moves with the rate as it does for that account (a per-order commission's cost in R, slippage beyond a quote's size, and the thresholds of a size rounding to zero or below the instrument's minimum). Changing the risk, the dataset balance or the conversions changes the dataset fingerprint, so the model retrains rather than being reused.

A decision hands over its trade without a quantity: `decision.trade()` has the target's instrument, side, exits, time limit and one R, none of which the strategy can change, and its send tags the entry with the decision's expected R (`EXPECTED_R:0.42R`, read by `orders::entry_expected_r`), which a backtest's trades file carries (see [backtest](../backtest/README.md#trades-file)). The strategy sends it at a stake of its own and the config's rates, `decision.trade().send(self, stake, rates)`: the config's stake, `config.stake()`, or a multiple of it, `config.stake().times(k)`, picked by any rule of its own, the decision's `expected_r` (an `R`) among its inputs, and `config.rates()`. It is sized on the equity of the account its orders are checked against, converted into the instrument's P&L currency at those rates, as every trade is (see the [strategy guide](../strategy/README.md)); dataset targets use the same trade path at the reference stake (`Trade::send_at`). A strategy may also drop the trade. Changing its instrument, exits or holding time invalidates its models' scores; its size does not, every figure being in R. With a commission per order, R improves with size, so a strategy staking far from the reference trades at a different R than the model expected. Forward order and time events to the handle, time events first to the order module, and rearm open trades on start. IB exits and time closes are not reduce-only, in datasets as live; see [IB](../venues/ib/README.md#trading-and-warmup).

## Targets and datasets

A strategy has one `[model]` target: either a bracket with both take profit and stop, or a time-only trade. Time-only requires its own ATR beside the limit; a bracket owns its ATR and cannot have a redundant ATR beside it. ATR must warm within warmup. A lone exit or an exit beside the limit is rejected. Read prices from the decision. `Target` and `TargetConfig::validate` in [`targets.rs`](targets.rs) give the configuration shapes and validation details.

With one-minute decisions, `model.target.bracket.atr = { period = 14, bar_interval = "15m" }` sizes the bracket from 14 completed quarter-hour bars. At 10:15, both the training label and the executable order use the ATR including the bar just closed; at 10:16 they use the same ATR distance around the new entry reference. For a time-only target, set `bar_interval` in `model.target.atr` instead. Omit it to use decision-length bars. A distinct interval is refused if any ATR bar could close within 10 ms after a decision grid point, before the decision timer fires. Warmup must cover the period at the selected interval (3h30m in this example). Allow an extra bar when starting live between closes: a history request skips its partial first bar, and decisions wait if the ATR is still cold.

A dataset run opens long and short target trades at each decision on a simulated hedging venue, each at the reference stake of the dataset balance. Exits may mix basis-point and ATR distances and are rounded to the nearest tick; a bracket's ATR argument table is allowed only when an ATR distance is used. ATR bars derive from the traded instrument's declared quotes, trades or compatible source bars. Cold or zero ATR, no reference price, an exit rounded to the reference price, or a reference size of none leaves the target unsettled; dataset runs log the reason, while live decisions suppress it. A missing instrument errors before orders. Inverse instruments, and commissions in a currency other than the instrument's P&L currency, fail dataset startup and error at live decisions: a commission is not converted. A dataset balance in another currency is converted at each decision's rate (see [reference stake](#reference-stake-and-the-strategys-stake)): dataset runs replay the pairs as the data requirements carry them, a cTrader pair's quotes, an IB pair's 1-minute BID and ASK bars, and keep no base currency, their account frozen and margining nothing, since the target converts the balance and nothing else reads one. A decision with no rate, before a pair's first quote or, for an IB pair, its first BID and ASK bars, sets no target: a dataset run logs it and stores no row, so a day with no rate builds no rows, as a day with no data of the instrument does; live, the decision is not made, its reason logged. A dataset balance whose currency the pairs do not reach the P&L currency from fails dataset startup, refused by the check a backtest's `--balance` passes (`backtest::refuse_balance`, Nautilus' exchange-rate path search through the pairs' definitions): the backtest and `train` commands refuse it before any build, naming its currency, the pairs read from the catalog, and `live` before any node is built. See [`targets.rs`](targets.rs) for order IDs and target mechanics.

**A dataset run's account is frozen and margins nothing.** Its venues set Nautilus' `frozen_account`, so no trade of the run moves the balance: the long and short opened at every decision lose their spread and commission without draining it. Its leverage is the largest a `Decimal` holds, so under Nautilus' default margin model every order's margin rounds to nothing and the risk engine denies none for margin, while keeping its other checks. Nautilus offers no margin-free model to a `BacktestVenueConfig`. A dataset run opens both sides at every decision, at all hours, which no account trades; whether an account can margin a trade is checked by the strategy's backtest, at its balance and its instruments' margins, and by the live venue. Margin changes no row, only whether one exists, so dataset runs take no leverage and it keys nothing.

**A denial fails the dataset run.** When Nautilus' risk engine denies a target's order, for a quantity below the instrument's minimum, say, the run stops (`shutdown_system`) and the build fails with the denial's reason: a reference stake the venue would refuse is a config fault, and a missing row would bias training. Raise the dataset balance (`[model] dataset`) or the risk.

**The config declares its dataset venue.** `[model] dataset`, such as `dataset = { commission = { per_quantity = "0.035 USD" }, balance = "10000 USD" }`, is the commission (`per_order`, `rate` or `per_quantity`, read as the backtest's flags read them) and balance of its dataset runs: the commission their targets, the payoff features and a decision's are net of, in the traded instrument's P&L currency, and the balance their reference stake is of, in that currency or one the pairs of `[trade] conversions` reach it from. An optional `latency`, such as `latency = "150ms"`, a positive duration as the config's others, delays each order command of its dataset runs by that much on its way to the venue, as a backtest's `--latency` does (see [backtest](../backtest/README.md#fills-and-costs)): an entry or a time close then fills on the first quote after its arrival. Left out, there is none. It keys the dataset and the stores, so `train`, a backtest's retrains and a live node, and its retrains, read the one store of the config, and none takes the commission, balance or latency as a flag; a backtest's `--commission`, `--balance` and `--latency` charge, stake and delay its simulated account alone. Training for another account is another config. See [backtest](../backtest/README.md) for fee options and rounding.

At a latency, a decision settles later than its time limit: its time close reaches the venue the latency after the limit and is processed at the run's next settlement point, within a minute, the run's execution engine purging its cache every minute by a timer, which releases every command due. A build replays its last day that much further, and a day is cached only once a replay has passed its end plus the limit, the latency and that minute, so a day's rows are those of every build replaying it. A limit shorter than the latency and that minute is refused at load: the time alert could fire while the entry is still on its way to the venue, which Nautilus counts neither open nor filled, so the alert would neither cancel nor close it and the entry would fill with no time limit. The limit need not be shorter than the decision cadence: the dataset's hedging venue keeps each decision's targets separate, even when their lifetimes overlap. The executable entry check does not filter dataset rows.

**At a latency, the fast moves leave no row.** The exits are set at the decision, from its reference price, and reach the venue with the entry as one bracket, the venue releasing them when the entry fills. When the price has moved through an exit by the time the delayed entry fills, that exit is already in the market: the stop is rejected, as dataset venues keep Nautilus' `reject_stop_orders`, and on cTrader and OKX the post-only take profit is rejected as a taker. A rejected order unsettles its decision, so the decision stores no row. The decisions dropped are those the market moved fastest after, so a dataset built at a latency is biased against them, and its models never learn from them. Without a latency the entry fills on the quote the exits were set from, so they are not in the market. Whether to keep such decisions, and how, is left open.

The target appends each side's payoff features to the strategy features without declaration; the meta model reads strategy features without them. Brackets include take-profit R and nominal stop loss before overshoot; every target includes entry cost. They account for spread and commission relative to each side's unit: long enters at ask, short at bid; trades or bars without quotes have no spread. See `PayoffFeature` and `TargetSetter::payoff` in [`targets.rs`](targets.rs) for payoff names and formulas.

A row is self-contained: features and times plus each side's payoff, net P&L, commission, exit and unit. A payoff width mismatch is an error; `DatasetRow` in [`dataset.rs`](dataset.rs) specifies the columns. Unit is the exact, unrounded reference quantity × multiplier × one R in P&L currency: stop distance for brackets, ATR for time-only, as the entry's `R:` tag holds it. Sub-cent units are valid; realized R is P&L divided by unit. A row settles only after both sides close. Rejected or unfilled entries, an in-market rejected stop, or positions still open at run end leave no row; inspect logs rather than assuming a row per decision. Bars-only fills are optimistic, including high before low; see [backtest](../backtest/README.md).

Datasets are keyed by strategy and fingerprint and stored by day. A build replays from feature warmup before the first missing day through the target limit after the last, storing only requested decision days. Supply prior history in the catalog: replay does not check or request it. Recursive features such as EMA or Wilder ATR never entirely forget their start; roughly 5 to 10 times the longest recursive period makes dependence negligible, not bit-identical. Running sums can also differ in their last bits.

Rebuilding deletes covered day files before writing because the catalog skips existing files. Do not consolidate the dataset directory: that loses day intervals. A train at `t` uses decisions before `t` settled by `t`; incomplete days are replayed to `t` and not cached complete. Concurrent builders can race on day files and manifest. Do not backtest against a catalog and store a live node is retraining into simultaneously.

## Training

Each enabled side regresses realized net R at the reference stake. The window `W` ending at `t` ends in a calibration slice `C` long (`[model] calibration`): fit on the decisions of `[t−W, t−C)` settled by `t−C`, calibrate on those of `[t−C, t)` settled by `t`. The meta splits its own window by its own `[model.meta] calibration` the same way. This purging prevents leakage, and the target limit separates window decisions from first model use. The limit must be shorter than both training and meta windows; each level's calibration plus the limit must be shorter than its window, so that its fit slice can hold a row.

There is no holdout and no per-refit gate. A gate judging each refit on a short final holdout withholds the freshest data from the fit, selects refits on noisy samples, and keeps an incumbent indefinitely on refusal without checking it on recent data; out-of-sample evidence is a backtest of already-trained models over a range the operator chooses (see [Scores](#scores)). A train fails, the whole model set publishing nothing, only when a fit or calibration slice has fewer rows than its level's `min_rows` (`[model]` and `[model.meta]`, required, at least 1; a meta's out-of-fold pair, see [meta-labeling](#meta-labeling), held to the sides'), the error naming the slice, its count and the minimum, and the out-of-fold pair if it is its; when a prediction on the calibration slice or the calibration is not finite; or when a model reloaded from what it saved does not reproduce its probes, the check a reader makes before use. The old `holdout`, `min_trades` and `min_expectancy` keys are refused at load as unknown.

A train publishes one model set, valid from its retrain time: its enabled sides, their pair's calibration and its meta when configured, or nothing. A failure of any of them, the meta's or its out-of-fold pair's included, publishes none of them and keeps the current model set. A model set is self-contained: its models are fixed as of its retrain time by that train, from the data and the config alone, none taken from or changed by another model set, and a train reads nothing of the store but whether its model set is already published. Joint calibration fits level and side-call slopes clipped to `[0, 1.5]`; a two-sided pair ties when both sides' predictions are constant, and a one-sided model fits its level line alone. Each model's manifest carries its baseline, the mean R of its fit and calibration rows, which its scores are read beside, and probes from its calibration slice; the pair's calibration is the model set's. See [`train.rs`](train.rs) and `StoredModelSet` in [`store.rs`](store.rs).

### Scores

Backtest scores are out of sample on models already in the store, the evidence on a config's edge: each period scores the model set in use in it, the latest valid at each decision, so a retrain time the store lacks scores the model set before it through its period. They use the same decision path: each picked trade counts once for its side before meta, and ties count for neither. Each side's all-trades baseline and prediction metrics cover all eligible rows with a model set. Meta prediction metrics cover all rows with a side pick whose model set holds a meta model; meta earnings count trades whose expected R passes its margin in R. Earnings are in R, each trade's net P&L over its unit, through Nautilus' `Expectancy` and `WinRate`, so they describe a model alike at any size or balance; skill, mean `R - E'`, calibration slope and top-decile gap are defined by `ExpectedScore` in [`score.rs`](score.rs). Scores at 1.5 times commission use the same picks. These figures describe the target decisions at events; the strategy's own report differs from them only where it filters the model's answer on account or execution state. Models and their own persisted fitting-and-calibration mean R baselines are scored on the same rows. A row whose model set fails its load checks is scored by none, as the handle decides no trade there. This applies even to off-grid publications or failed retrains.

### Meta-labeling

Side models are the primary decision; a meta model can filter their chosen trade for any target, not replace them with a rule primary. When the model is asked is the strategy's event filter, which the handle evaluates at the grid tick (see [Cadence and decision](#cadence-and-decision)). A train at `t` with a meta of window `Wm` fits an out-of-fold pair of the sides as of `t−Wm`, as a train at `t−Wm` fits them: on `[t−Wm−W, t−Wm)` with the sides' settings and split, held to the sides' `min_rows`. The out-of-fold pair decides every row of `[t−Wm, t)` settled by `t` through the decision path, its picks before any meta, and those picks are the meta's rows, excluding decisions with no pick; then the sides are fitted as of `t`, and the model set ships them beside the meta. The out-of-fold pair is not stored, and the meta's manifest records its time (`out_of_fold`). This is stacking practice, the pair named after its out-of-fold predictions: the second level learns from the first's predictions of rows it was not trained on, here the out-of-fold pair's, while the traded sides stay as fresh as a strategy's without a meta, at the cost of a meta learned from sides up to a meta window older than those it filters. The meta's rows contain strategy features, picked side and calibrated `C'` and `D'`, not target payoff features. The meta regresses the picked trade's net R and fits its own one-sided calibration line. It takes the decision's trade when its calibrated expected R is at least its margin, in R (`margin = "0.2R"`); how much the trade stakes is the strategy's. It is split, held to its `min_rows` and checked as the sides are. Every model set of a strategy with a meta holds one, from its first train on, and a publish without one is refused. A non-finite expectation means no trade, and a meta decides only beside the sides of its own model set. Legacy probability `threshold` and meta `size` are rejected: use the margin, and the strategy's stake.

### Scheduling

Training is the `train` command alone, a step of its own before any backtest: a backtest trains nothing, so it never trains over the range it judges, and runs on what the store holds (see [backtest](../backtest/README.md#model-retraining)). `train --at t` trains at one time; `train --from a --to b`, periodic strategies only, trains at each retrain time of `[a, b)` in time order, the same times a backtest from `a` to `b` trades on: the last on the grid not after `a`, then each before `b`. Each is planned on the store the trains before it left, and reported as it ends; one that fails does not stop the next, and the command exits nonzero at the end, listing each such time with its reason. A model set already published at a retrain time, under the same dataset fingerprint and model set key (see [store](#store-validity-and-versions)), is not trained again and is reported as already published: a train is deterministic, so it would come out the same. A second train over a span trains nothing; one over a span starting earlier trains only the times added.

`train` reports run figures, not performance figures, one block per retrain time, so that training and evaluation stay apart and a train can be sized against its interval; a config's edge is judged by a backtest's scores (see [Scores](#scores)), and the fitted calibration stays in the model set's manifest. A block opens with `the train at <t>:` and the model set published, its directory, the model set already published, or the failure and its reason, then the figures the train reached, a failed train's as far as it went: the wall time, the CPU time, user and system, and the peak memory of the train process; the dataset days it read, built by its replay, from the first the dataset lacked to the last, or taken from the cache before it; and the rows of the fit and calibration slices of the sides fitted at `t`, the long's and the short's being the same rows, of the out-of-fold pair and of the meta, each beside its level's `min_rows`. The process figures are read once at a train's end: the wall time from Nautilus' real-time clock, the CPU time and peak memory from `getrusage` of the process, which Nautilus does not read, on Unix alone, reported as not measured elsewhere. Over a span, a block's wall and CPU time are those since the block before, the first's since the command started, and the peak memory is the process's high-water mark so far. See [`report.rs`](report.rs).

Live, a retrained strategy's node trains each retrain time `t` as `train --at t` does: the model set is stamped `t` and its data cut there, so a backtest over the same span loads the very model sets live traded on, and `train --from --to` rebuilds any live skipped. When a live train starts, and what decides until then, is the retrain actor's wait rule (see [live](../live/README.md#retraining)).

A train at `t`, periodic or never retrained alike, keeps the model set valid exactly at `t`, whole, reporting it already published, or trains one, with its meta from the first train on (see [meta-labeling](#meta-labeling)); an older model set in the store does not stop it, and still decides before `t`. A model set whose manifest is missing, from a train stopped before it, is not listed and is trained again. The train replays once from the earliest needed fit, the out-of-fold pair's with a meta, or not at all if it keeps a model set. It exits successfully when all models are published or already published; a failed train produces a nonzero exit.

Omit `retrain` for a never-retrained strategy; if present, the interval must be positive. Its train at `t` is a periodic train's: it publishes a model set valid from `t` unless one is already published there, its sides fresh at `t` and, with a meta, the meta on its out-of-fold pair's picks; the operator chooses when to train it again.

A never-retrained strategy has no retrain times: it trains with `train --at` alone, and `train --from --to` refuses it. Its backtest's scores cover one period using each model's own baseline. Live never-retrained strategies have no retrain actor, timer or launched train; externally published models are picked up at the next decision, subject to the usual bar delay. See [live](../live/README.md) for retrain operations.

## Store, validity and versions

The dataset fingerprint includes ordered feature names and sources, normalized parsed feature-table arguments, feature version and warmup, decision rule and nonzero bar-build delay, target and ATR inputs and the risk of its reference stake, dataset version, and the normalized commission and balance of `[model] dataset`, and its latency when it declares one, so that a config without one keeps its dataset and stores, and the pairs of `[trade] conversions`, in their order, when it lists any, likewise. Indicator tables used only by strategy logic are excluded. A strategy's model sets are keyed by that fingerprint and its model set key: every training setting of its models, the sides' learner, retrain interval, window, calibration and `min_rows`, both side margins in their R text, the meta's learner, window, calibration, margin and `min_rows`, or no meta, and `store::VERSION`. Never-retrained stores are partitioned from periodic ones. Changing any of these selects another model set key rather than silently reusing incompatible results.

`ModelStore` owns the model sets, schemas, fingerprint and their listing. A model set is a directory `<valid from>/` holding the directory of the publish that wrote its models' files, named by process and publish, and `model_set.json`, its manifest, written last, once the models' files are synced to disk, and renamed into place: the manifest is the commit marker, so a model set without one is not listed, a crash or power loss never lists one whose model files are cut short, and concurrent publishers never mix their files. An unreadable store fails handle construction. At each decision the handle lists the model sets again and swaps to the latest valid at that boundary, its sides and its meta together, so no meta decides beside sides of another train. A failed listing logs and retains the previous list; a model set already listed can still swap in.

Before use, the handle checks each model of the model set: fingerprint, ordered feature names and width, and reproduces stored raw pre-calibration prediction probes bit for bit; a side's model holds no calibration of its own, its pair's being the model set's, and the meta holds its level line. A newest model set failing any check stops new entries: the decision errs, naming the model set and the check, which Nautilus logs, the model set before it is not used either, and the model set is read again at the next decision, so it is used once it loads. To mend it, remove its `<valid from>/` directory and train it again: a train skips a model set already published at its time, so training alone leaves it as it is. Open trades finish on their exits. With no valid model set, no side trades.

Bump the strategy's feature version when feature computation changes without a corresponding name, warmup or config change. Changed table arguments are already keyed; a value-preserving rename or refactor needs no bump. Bump `store::VERSION` for model file, manifest or read-format changes: models retrain, but datasets remain. Bump `dataset::VERSION` for shared row-producing changes, including Nautilus indicator, matching or fill changes, or dataset manifest changes. When rows or their version are affected, update and commit the golden snapshot with the version:

```sh
GOLDEN_ROWS=write cargo test --test backtest backtest_golden_rows::
```
