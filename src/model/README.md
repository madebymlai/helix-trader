# Model strategies

Read the [strategy guide](../strategy/README.md) first for config, series, orders, bars and warmup. This guide covers the model-specific contracts; [`model_ema/`](../strategy/model_ema/) and [`config/model_ema.toml`](../../config/model_ema.toml) show their use. For walk-forward command orchestration see [backtest](../backtest/README.md); for live retraining operations see [live](../live/README.md); for futures calendar and transitions see [rolls](../rolls/README.md).

## Authoring and decisions

A model strategy's `Part` sets `TAKES_MODEL`, builds the shared `FeatureSet` through `ModelPart::features`, and delegates `Part::reads` to `model::reads`. Implement `ModelStrategy` with the same features in each mode; `ModelHandle` owns the decision path, not order submission. Register the strategy in `main.rs` for dataset, train, backtest and live as in the example.

Build features once in an ordered `FeatureSet`, with sources, feature-code version and warmup. Each indicator feature comes from a declared table: `.quotes(instrument_id, DECLARED, &config.indicators)`, and likewise `.trades`, `.bars`, `.depth` and `.deltas`, builds the table's indicator, names the feature and fingerprints its arguments; no call takes an indicator built by hand. The code decides which features exist and which series each reads; a table adds or removes none. A feature is named after its table when the table feeds it alone, and `<series>:<table>` when the table feeds several (a bar type, or `QuoteTick of <instrument>`). Custom-data features (`.data`) keep the name the code gives them. A feature is a Nautilus indicator exposing `Feature::value`; built-in moving averages already do, and a custom one brings its own argument type. The set registers bars, quotes and trades as indicators. Forward book depth, deltas and custom data to it from the corresponding handlers, including historical responses; warmup-built bars need forwarding too. The declared features and the barrier ATR determine the series read and checked against config. Traded-instrument quotes added by the shared data requirements are not extra declared series.

A cadence is epoch-aligned and fires after the bar-build delay and a small margin, so a decision sees the bar closing on its grid in both replay and live. Cadence decisions require fresh market data of the traded instrument since the preceding grid point; custom data and another instrument's activity do not establish freshness. Event decisions are fresh by definition. Cold features or stale data produce no row or trade. Root tick features reset on a roll and must initialize on the new contract before deciding; see [rolls](../rolls/README.md).

The handle publishes a feature row and, in trading mode, returns a decision using the latest valid model for each enabled side. Expected net P&L combines calibrated win probability with expected win and loss; for a barrier it scales the payoff in R by the decision's stop worth. A side must clear its configured margin; the higher expectation wins and a tie yields no trade. No valid model, cold ATR, or a rounded exit at the reference price also yields no trade.

Send `decision.trade()` through `strategy::orders`: it has the target's instrument, size, exits and time limit. Dataset targets use the same trade path. Changing size, exits or holding time means the actual trade is not the labelled trade: the model's holdout and expected P&L no longer describe it. Forward order events and time events to the handle, and time events first to the order module; rearm open trades on start. IB's execution client rejects the reduce-only orders needed here, so model strategies cannot trade live on IB; see [live IB](../live/ib/README.md).

## Targets and datasets

A dataset run opens long and short target trades on Nautilus' simulated hedging venue at each decision. Barrier exits are distances in basis points or ATR multiples from the decision price, rounded to the instrument's tick grid; a horizon closes at its limit. ATR bars are derived from the traded instrument's declared inputs at the decision cadence. An uninitialized ATR or exit rounded to the reference price produces no target. Dataset outcomes are realized P&L net of simulated commission, with exits, commissions, barrier distances and settlement times. Denied, rejected or unfilled entries and positions still open at stop leave decisions unsettled; inspect logs rather than assuming every decision became a row. Bars-only fills are optimistic, including high before low; see [backtest](../backtest/README.md).

Datasets are keyed by strategy and fingerprint and stored by day. A build replays from feature warmup before the first missing day through the longest target after the last day, storing only decisions in the requested days. Ensure the catalog contains that prior history: replay does not check for it or request missing data. A recursive feature such as an EMA or Wilder ATR never completely forgets its starting state; use roughly 5–10 times the longest recursive period for negligible, not bit-identical, start dependence. Even a running sum can differ in its last bits across builds.

Rebuilding deletes the existing covered day files before writing because the catalog otherwise skips existing files; do not consolidate the dataset directory, since that loses day intervals. A train at `t` uses only decisions before `t` settled by `t`. Incomplete days are replayed to `t` and not cached as complete. Concurrent processes building the same strategy's dataset can race on day files and the manifest: do not backtest against the catalog and store a live node is retraining into at the same time.

## Training and acceptance

Each enabled side learns whether its labelled target trade gains net of costs. The training window ends at `t`; its final holdout is preceded by an equally long calibration interval. Fit only on rows before calibration that settled by calibration start, calibrate on calibration rows settled by holdout start, and judge on holdout rows settled by `t`. This purging prevents target outcomes from leaking across boundaries; the longest target also separates the window's decisions from first model use. Target duration must be shorter than the decision cadence, so trades labelled separately on the hedging dataset venue do not overlap in a live netting account. The window must leave fitting data before calibration and holdout.

Publish a side only if holdout calibrated log loss beats the training-mean baseline, its selected trades meet `min_trades` and `min_pnl`, and their net P&L per trade exceeds that of all side trades. AUC is reported, not an acceptance gate. Holdout also reports the same selected trades under 1.5 times commission; this is a stress report, not another selection. A rejected or failed train keeps the current model, independently for each side. Barrier payoff uses each row's stop worth; inverse instruments are refused for barrier labels.

Meta-labeling lets a primary choose a side and a meta model decide whether to take its barrier trade. The primary can be a model or a rule; rule features declare `.primary()` and use `decide_on`. A model primary must itself be barrier-labelled. Meta rows use the primary model valid at each historical decision, out of sample, and exclude decisions where it would not trade; rule rows come from its signals. The meta model is calibrated and accepted on its own holdout, and a missing valid meta model means no trade. Optional sizing scales the target quantity by the meta probability; interpret the labelled trade's economics accordingly.

## Store, validity and versions

The dataset fingerprint includes ordered feature names, the series each feature reads (so a feature named after its table alone still keys its bar type or instrument), the parsed arguments of each feature table (serialized, so `"15m"` and `"900s"` match; tables built for the strategy's own logic are excluded), feature version and warmup, decision rule, targets and their ATR inputs, dataset version, and normalized dataset venue costs, balance and leverage. Model store settings also key learner, label, retrain interval, window, holdout, acceptance minimums and side margin. A meta model's store is keyed by its primary's retrain interval, a model's or a rule's, so a weekly-retrained strategy never trades on a model a daily-retrained one published between its retrains (`store::tests::a_store_lists_only_the_models_of_its_retrain_interval`). Changing these selects different data or models rather than silently reusing incompatible results.

A published model has a valid-from time and is written by rename. At each decision the handle selects the latest valid model and swaps only at that boundary. Before use it checks fingerprint, ordered feature names and width, then reproduces stored prediction probes bit for bit. A model failing parity is refused and the current one retained. A side with no valid model does not trade.

Bump the strategy's feature version when feature computation changes without a corresponding name, warmup or config change, such as a different input or formula. A changed feature-table argument is config and needs no bump. A rename or refactor preserving values needs no bump. Bump `dataset::VERSION` when shared row-producing behavior changes for the same data and config: decisions, targets, fills, exits, P&L, commissions or shared features, including a Nautilus pin change affecting indicators, matching or fills. After the appropriate bump, update the golden rows and commit both version and snapshot:

```sh
GOLDEN_ROWS=write cargo test --test backtest backtest_golden_rows::
```
